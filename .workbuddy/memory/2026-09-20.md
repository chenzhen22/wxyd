### 本次特意写准的几个点（dmidecode 专有坑）

- **必须 root**：读 `/dev/mem`，普通用户直接 Permission denied。
- **DMI 类型编号要记对**：`-t 16` 是「物理内存阵列」（总量 + 槽位总数），
  `-t 17` 才是「单根内存条」；`-t 6` 是旧 SMBIOS(<2.1) 的内存模块，现代机器基本为空。
  报内存盘点要看 17，别写错成 16。
- **厂商占位值必须过滤**：`Not Specified` / `To Be Filled By O.E.M.` / `Unknown` / `None`
  都不是真值，脚本里统一回退成 `unknown`，否则资产表会混入垃圾。
- **虚拟机/云主机上不可信**：KVM/QEMU 下 Manufacturer 常为 QEMU/Bochs，
  内存 `Speed` 显示 Unknown（虚拟内存无物理频率），Chassis/Power Supply 整段缺失。
  取 UUID 和机型可以，容量类数据要改用 `lscpu`/`free`/`lsblk`。
- **`Configured Memory Speed < Speed` 就是降频信号**，通常是混插了不同频率的内存条 —— 这是排查时最该看的一行。

### 工具层踩坑：校验脚本的正则

今天自写的校验脚本里 `^### ... \n\`\`\`bash\n(.*?)\`\`\`\n((?:- .*\n?)*)` 配了 `re.S`，
导致 `- .*` 里的 `.` 匹配换行、**一口吃掉全文**，只匹配出 1 条语法（实际 7 条）。
教训：在 DOTALL 模式下，行内匹配一律改用 `[^\n]*`；跨行的代码块才用 `[\s\S]*?`。
**校验脚本自身出错会伪装成「内容有问题」，看到条数明显偏少先怀疑正则，别急着改 md。**

### 关键坑 1：JVM 信任库不含 CFCA 根（花较多时间）

- 症状：`curl` 访问正常（`ssl_verify_result=0`、严格校验也 200），但 Java 侧报
  `SSLHandshakeException: PKIX path building failed`。
- 原因：证书链是 `*.kshbank.cn → CFCA OV OCA → CFCA EV ROOT`（服务器把自签名根也一并下发），
  而 **JDK 1.8.0_181 的 cacerts 共 105 个条目，其中没有任何 CFCA**。
  curl 走系统信任库所以能过 —— 这就是「命令行能通、程序不通」的典型原因。
- 解法（**不要关证书校验**）：把 CFCA EV ROOT 提取为 `resources/certs/cfca-ev-root.pem`，
  `ExtraTrustStore` 组合「额外信任库 + JVM 默认信任库」，**只追加可信锚点**，
  主机名校验、有效期校验、链完整性校验全部保持开启。
- 该根自签名，有效期至 **2029-12-31**，SHA-256 指纹 `5C:C3:D7:8E...:FD:70:FD`。
  以后要再补证书，往 `resources/certs/` 放 `.pem` 即可，**无需改代码**。
- 启动日志会打印：`已加载 1 张额外根证书，将与 JVM 默认信任库合并: [CN=CFCA EV ROOT,...]`

### 关键坑 2：网络失败的错误提示不能写死

初版把所有 `IOException` 都提示「可能是证书问题」，导致 DNS 解析失败也提示去关证书校验。
已改为按异常类型分派：`SSLException/PKIX`→证书、`UnknownHostException`→DNS、
`SocketTimeoutException`→超时、`ConnectException`→端口未开放。

### 验证方式（本功能的验收套路）

- **独立基准交叉校验**：先用 curl 把页面存下来、本地解码算 SHA-256，再调接口比对返回文件。
  本次两侧均为 `d9929d496e08cc180860fa272b5098bd4b938929ba2ca444a22110723f5f23b9`，
  大小 3,077,633 字节一致。
- **7z 结构深度校验**：`32 + nextHeaderOffset(3077536) + nextHeaderSize(65) == 总长 3077633`；
  End Header 首字节 `0x17`（kEncodedHeader）= 结构完整可用。
- 反面用例：元素不存在→422、非法协议(file://)→400、空网址→400、不可达主机→502、未登录→401。
- 静态资源探活：`/api/api.html` 与 `/api/Assets/js/archive.js` 均 200。
  **注意静态资源在 context-path `/api` 之下**，别写成 `http://localhost:8090/api.html`（会 404，我踩过）。

### 本次特意写准的几个点（uname 专有坑）

- **uname 不给发行版信息**（最大误会）：`uname -a` 只说 `Linux`，想知道 Ubuntu/CentOS
  必须读 `/etc/os-release` 或 `hostnamectl`。脚本里 `uname -a | grep -i ubuntu` 基本不可能命中。
- **`-p` / `-i` 在多数 Linux 上是 `unknown`**：别用它判断 CPU；架构一律用 `-m`。
- **容器里是宿主机内核**：容器与宿主共享内核，`uname -r` 显示宿主机版本而非镜像的。
  判断「是否在容器内」要用 `/.dockerenv`、`/proc/1/cgroup`、`/proc/1/comm`。
- **`uname -a` 各平台字段顺序/内容会变**，只适合人看，脚本里要解析就逐项取 `-s/-n/-r/-m`。
- **内核版本比较必须用 `sort -V`**，字符串比较是错的（`"5.9" > "5.15"`）。
- macOS(BSD) 差异：不支持 `-o`；`sed -i` 必须跟一个空参数 `sed -i '' `。
  Windows Git Bash 的 `uname -s` 形如 `MINGW64_NT-10.0`。

### 又一次被自己的校验正则坑到（第二次）

`(?:- 描述:...\n)+```bash` 这种写法**要求描述行后紧接围栏**，但实际 md 里描述行与围栏之间
有一个空行，导致示例段匹配出 0 条。上一轮（dmidecode）之所以「碰巧」能跑通，
是因为当时误加了 `re.S`，让 `.*?` 跨过了空行 —— 属于用错误的宽松掩盖了错误的严格。
**正解：`\n+` 显式吃掉空行**，即 `### 标题\n+(-\s*描述:[^\n]*)\n+```bash\n([\s\S]*?)``` `。
另：用 bash heredoc 传 Python 脚本时出现过解析异常（全库 name 统计为 0），
**校验脚本一律写成 `.py` 文件再执行**，别用 heredoc。
