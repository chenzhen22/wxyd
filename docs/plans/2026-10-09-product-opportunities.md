# wxyd 产品与市场机会分析

日期：2026-10-09
性质：机会盘点 + 优先级建议（非 PRD，立项前需逐项细化）

---

## 1. 现状盘点：wxyd 是什么

**一句话**：面向开发者/运维的自托管个人驾驶舱 —— 知识沉淀（记忆笔记 v2 / Java API 速查 / Shell 速查）、运维工具（SQL 查询 / Dubbo 泛化调用 / 归档下载 / PDF 工具）、内容消费（福利专区）、轻协作（群聊 / 留言板），PC + H5 双端，国密 SM4 加密，单 jar 部署。

**客观规模**：注册用户约 8 人，本质是「自己 + 小圈子」的自用系统。这决定了下面所有判断的边界 —— **自用价值优先，规模化次之**。

**资产盘点（做新功能时先看手里有什么积木）**：

| 积木 | 状态 | 可衍生的方向 |
|------|------|-------------|
| dataScan 爬虫（linux.do 福利羊毛，每小时入 MySQL） | 已上线 | 通用化订阅、关键词推送 |
| 钉钉机器人模块（access_token + SM4 加签） | 已上线 | 任意消息推送出口 |
| SMTP 邮件（邮箱注册已用） | 已上线 | 第二推送出口 |
| 笔记 v2（全文检索 / 摘录 / 双链 / 导出） | 刚完成 | 一键归档、每日回顾 |
| 群聊（轮询、图片） | 已上线 | 机器人播报进群 |
| 菜单四态管控（可见性/白名单） | 已上线 | 新模块灰度发布 |
| H5 移动端（全模块覆盖） | 已上线 | PWA 化 |

## 2. 市场参照系与定位

**同类对照**（自托管圈）：

| 对标 | 它做什么 | wxyd 的差异 |
|------|---------|------------|
| Notion / 语雀 | 通用知识库 | 重、云依赖；wxyd 轻、数据全自持（md 文件为真相源） |
| Obsidian | 本地双链笔记 | 无 Web/移动端协作；wxyd 有 H5 + 摘录闭环 |
| Dashy / Heimdall | 纯导航面板 | 只是入口聚合，无业务功能；wxyd 每个入口都是真功能 |
| UptimeRobot | 监控告警 | SaaS、数据在别人手里；wxyd 可自建巡检 |
| RSSHub + TTRSS | 自托管订阅 | 通用订阅无清洗；dataScan 已带清洗+去原站信息 |

**结论（定位判断）**：wxyd 不该去卷任何一个单品类，它的护城河是**「运维场景垂直 + 全家桶自持」**——一个人在自己服务器上，把日常运维要用的知识、工具、资讯、监控收敛到一个入口。新功能都应该强化这个定位，而不是往外扩。

## 3. 机会清单（按推荐度排序）

### 🥇 O1 羊毛雷达：订阅关键词 → 钉钉/邮件推送

- **为什么是第一**：三块积木全齐（dataScan 数据 + 钉钉机器人 + SMTP），只差一个"规则匹配 + 定时推送"的粘合层，约 1–2 天工作量；且把福利区从「被动刷」升级为「主动推」，高频刚需（羊毛信息时效性极强，晚看到 = 没了）。
- **做什么**：用户自建订阅规则（关键词/分类），后端定时任务每小时（或对齐 dataScan 频率）扫描新帖，命中即按用户偏好推钉钉或邮件；推送带去重（post_id 已推不重推）。
- **表**：`welfare_subscribe(id, user_id, keyword, channel, last_post_id)`，复用现有 MyBatis。
- **风险**：钉钉限流（自有机器人 20 条/分钟，足够）；规则爆炸（限 10 条/人）。

### 🥈 O2 服务器巡检与到期提醒日报

- **为什么**：平台的使用者是运维，"每天早上一条钉钉日报：3 台服务器磁盘 >80%、域名 x.com 15 天后到期、证书 y 30 天到期"是运维最稳的日频需求；对标 UptimeRobot 但数据自持。
- **做什么**（分期）：
  - V1 纯后端：巡检任务清单（URL 存活 / 端口 / 域名 WHOIS / SSL 证书过期天数 / 磁盘——通过 SSH 或 agent），每日定时跑，异常 + 到期汇总成一条钉钉/邮件日报；
  - V2 加"资产台账"页面（服务器/域名/证书 CRUD，含到期日）；
  - V3 agent 上报（可选，后置）。
- **规模**：V1 约 2–3 天。与 O1 共用推送通道（做完 O1 这个顺水推舟）。

### 🥉 O3 SQL / Dubbo 结果一键归档到笔记

- **为什么**：知识库 v2 建立了「资料页 → 笔记」的摘录模式，但最高频产生"值得记的东西"的两个场景——SQL 查询结果（排查结论）和 Dubbo 调用样例——目前只有 Dubbo 桌面端有入口，SQL 页完全没有。
- **做什么**：sqltool 查询结果卡片加「存入笔记」（结果表格转 md 表格 + SQL 语句），复用 `note/saveFromSource`（sourceKey=sql/query，白名单加前缀）。半天工作量，让知识库真正成为"排查完顺手存"的终点。

### O4 H5 PWA 化

- **为什么**：手机加个桌面图标、全屏无地址栏、弱网有壳缓存 —— 半天工作量，日常使用感知极强（现在每次都要开浏览器输地址）。
- **做什么**：manifest.json + 简单 service worker（壳缓存，API 不缓存）+ 图标；iOS 注意 apple-touch-icon。

### O5 dataScan 通用化：个人订阅中心

- **为什么**：把"抓 linux.do 福利版"泛化为"抓任意 RSS/论坛版块"，wxyd 从"一个福利站"变成"我的信息枢纽"，壁垒上升一级。
- **规模**：3–5 天，且涉及 dataScan 仓库改造（跨项目）。
- **建议**：等 O1 上线验证推送价值后再投入。

### O6 笔记每日回顾

- **为什么**：知识库最大的敌人是"存了不看"。每天登录后推 3 篇随机旧笔记（或"去年今天"），零存储成本激活存量；对个人知识管理是高感知功能。
- **做什么**：后端 `GET /note/daily`（随机抽样 + 避免重复），PC 首页/H5 首页各加一个卡片。1 天。

### O7 全文检索升级（ngram）

- **现在不做**：当前 LIKE 子串匹配在百篇级完全够用；笔记量上千或多人共用时再上 MySQL ngram FULLTEXT（改 mapper 即可，检索层已收敛在 NoteSearchService，接口不变）。**记入技术债清单而非需求清单**。

## 4. 优先级矩阵

```
        高价值
          │
  O1 羊毛雷达 │ O2 巡检日报
  O3 结果归档 │
──────────────┼──────────────→ 实现成本低
  O4 PWA     │ O5 订阅中心
  O6 每日回顾 │
          │
        低价值
```

**建议节奏**：O1（本周可做）→ O3 + O4（一个下午）→ O2（下周）→ O6 → O5 观察后定。

## 5. 明确不建议做（Non-goals）

| 不做 | 理由 |
|------|------|
| 开放注册 / 社区化运营 | 8 个用户撑不起网络效应，反带来审核/安全/内容合规成本；现有"邀请制+审批"足够 |
| AI 问答 / 摘要 | 没有真实需求输入前是炫技；且需引入 LLM key 成本。等笔记量 >500 篇且"找不到"成为真实抱怨再议 |
| 通用导航站 / 仪表盘 | 与 Dashy 等正面竞争且无差异化，wxyd 的入口本来就都是真功能 |
| 多实例 / 分布式 | 单人规模，单 jar + SQLite 级心智是最优解，别给自己造运维对象 |
| 原站信息展示（福利区） | 已有设计原则（纯展示、不回链），维持——既合规又不给原站引流压力 |

## 6. 数据验证建议（做完 O1/O2 前先立个基线）

现在平台没有埋点，判断全靠体感。建议顺手加两个计数（logback 打点即可，不必建表）：
- 福利区日打开次数 / 详情阅读次数（验证"高频"假设）
- 笔记周搜索次数与零结果率（验证知识库是否真的被用）

有了这两条基线，O1/O2 上线后才有"值不值"的判断依据。
